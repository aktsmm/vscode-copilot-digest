Automations run agent tasks from a saved prompt and session configuration. Use them for work such as summarizing repository changes or triaging issues without starting each session manually. Run an automation on demand, on a recurring schedule, or, for cloud automations, in response to supported repository events. H2: Choose where an automation runs
You can choose to run an automation locally or in the cloud based on your needs:
GitHub service plans, permissions, billing, security, and supported triggers can change independently of VS Code. Review GitHub Copilot automations before enabling unattended cloud runs.
Automations start a run when a trigger fires. They are different from cloud sessions, where you start an interactive task and reopen the same session to continue it. Creating a cloud session doesn't create an automation or schedule.

H2: Create an automation from chat
Use the built-in /automate skill in the Agents window to turn a completed task or a new idea into a recurring automation. The agent helps draft a reusable prompt and configuration for you to review before saving.
Start in any of these ways:
Reuse a completed task: Enter /automate in the same chat. The agent uses the relevant goal, inputs, scope, and expected result, rather than saving the entire conversation. Add instructions after /automate to adjust what should repeat.
Start from a new idea: In a new chat, enter /automate followed by the task you want to repeat. If you enter /automate without context, the agent suggests examples and helps you define a task.
Start from the Automations view: Select Automations in the sidebar, and then select Create with Agent. This opens a new-session page with /automate prefilled. Add your task description and send the prompt.

H2: Start from a template
Automation templates provide a starting name, prompt, and schedule that you can review and adapt:
Built-in Templates contains templates included with VS Code.
Templates from Plugins contains templates from enabled Agent Plugins. Each template shows a Plugin badge and its source plugin.
The template sections start expanded when you have no saved automations and collapsed when you have saved automations. A blue marker on Templates from Plugins indicates that an enabled plugin contributed a new template. Expand the section to clear the marker.
Select a template to open it in the New Automation dialog. Review the prompt and schedule, and then choose the workspace, agent, model, permissions, and isolation. The Enabled checkbox is cleared by default. Select it only after you review the complete configuration, and then select Create.
Disabling a plugin removes its templates from the view. Automations that you already created from those templates and their run history remain available.
H2: Run and review an automation
Select Run now on the automation card. The automation starts an agent session, and its run appears under History.
Select a run in History to open its session. Review the response and any changes before relying on the task's output. If the session needs approval, review the request there. If a run fails, inspect its error and session before trying again.
Each run uses the selected agent and model, so account for recurring usage when choosing a schedule.
For a cloud automation, the automation card and its history update while a run is active and show whether the run is queued, running, completed, or failed. Select a run to open its session in the Agents window, review its output, and send a follow-up when available. A follow-up continues that run's conversation. It doesn't update the automation's saved prompt or future triggers.
Select Refresh to retrieve changes made on GitHub. On a run, use Open on GitHub to review or manage it there, or if the session isn't available in the editor yet. If a run reports Needs input on GitHub, open it on GitHub to respond.
H2: Set a recurring schedule
After checking the first run, select the automation's name to edit it. Choose a schedule from Trigger, keep Enabled selected, and select Save.
Daily and weekly times are displayed in your local time zone. Cloud schedules are stored in UTC. Review the saved time when your local UTC offset changes, such as after a daylight saving time change.
Cloud automations support Manual, Daily, and Weekly triggers. For daily and weekly cloud schedules, select a time with minutes set to 00, 15, 30, or 45.
For local automations, keep these execution requirements in mind:
Keep the machine that runs the automation awake and its agent available. Agent Host-backed schedules require a running Agent Host process. Other schedules require a running VS Code window. Don't assume that local automations continue after you quit the application.
After an interruption, a missed schedule can trigger a catch-up run. Don't rely on every missed occurrence being replayed.
An automation runs one session at a time. Another scheduled occurrence doesn't start a parallel run of the same automation.
Cloud schedules run on GitHub rather than through your local scheduler. You can close the Agents window or turn off your computer without stopping the schedule.

Set an end date for temporary work, such as a daily release summary that should run for two weeks. End dates are supported for automations on local or remote Agent Hosts, but not GitHub cloud automations.
Create or edit an automation, and expand Advanced Settings.
Create or edit an automation, and expand Advanced Settings.

Review the estimated end date and time, and then select Create or Save.
Review the estimated end date and time, and then select Create or Save.
The duration is converted to a fixed end date when you save, using your local calendar. Reopening the form or editing unrelated fields doesn't extend it. Changing the duration calculates a new end date from the time you save.
When the end date is reached, the automation disables future scheduled runs, including catch-up runs. It doesn't stop an active run or prevent you from selecting Run now.
To remove the end date, select Never under Disables after and save, or select More Actions > Remove end date on the automation card. Removing the end date doesn't re-enable a disabled automation.
To resume scheduled runs, set a future end date or remove it, and then enable the automation. If you enable an expired automation from its card, Remove expiration and enable removes the cutoff and resumes scheduling without an end date.

New cron schedules use your local time zone. When you edit an existing cron schedule, the form shows its saved time zone rather than replacing it.
After saving, the schedule remains Cron, even if its cadence matches a preset. To switch to a preset, select it explicitly in Trigger.
Use exactly five fields, separated by spaces, in this order:
Each field supports:
* for every value.
Comma-separated lists, such as 9,17.
Ascending ranges, such as MON-FRI.
Positive steps on * or a range, such as */30 or 0-59/15.
Steps from a single starting value, such as 5/15, aren't supported. Don't include a seconds field or aliases such as @daily.
When both the day of month and day of week are restricted, either can match. The month field still applies to both. For example, 0 9 1 * MON runs at 9:00 AM on the first day of each month and on Mondays, not only when the first day is a Monday.

H2: Share an automation
Export a local automation as a .automation.md file to reuse it on another machine or share it with someone else. The file is readable Markdown with YAML frontmatter and contains only portable information:
Name and prompt.
Manual, hourly, daily, weekly, or cron schedule.
An optional end date.
File format version and portable identifier.
Exported cron schedules use timeZone: local, so the importing machine uses its own local time zone. A cron schedule whose configured time zone differs from your current local time zone can't be exported.
Files with an end date use format version 2 and preserve the fixed cutoff, not a duration that restarts on import. Review or change the end date before enabling an imported automation.
The file doesn't include the workspace, provider, model, permissions, enabled state, or run history. The person who imports the file chooses these options locally.
Cloud automations don't offer Export. Manage their definitions and triggers on GitHub rather than relying on an exported .automation.md file to reproduce them.

H2: Manage an automation
Edit: select the automation's name, update its supported fields, and select Save. For time-limited work, set or change an end date. A cloud automation's repository and Owner can't change after creation. Create another automation to use a different repository or owner, and disable the original if it should no longer run.
Enable or disable future runs: select More Actions > Enable or Disable. Disabling an automation doesn't stop a run already in progress.
Duplicate: select More Actions > Duplicate, review the copy in the New Automation dialog, and select Create. Duplicate event-triggered cloud automations on GitHub to preserve their complete configuration.
Stop an active run: select Stop for the run in History when available. This requests cancellation, not a rollback of completed actions.
Export (local only): select More Actions > Export. For more information, see Share an automation.
Open on GitHub (cloud only): select More Actions > Open on GitHub to open the automation definition. Use this action on an individual run to open that run instead.
Delete: select More Actions > Delete and confirm. This permanently deletes the automation and its run history.
For cloud automations, edit, enable, disable, and delete actions update the automation on GitHub. Disabling a cloud automation prevents future scheduled runs but doesn't stop a run in progress. Deleting it removes the cloud automation and its schedule from GitHub. Select Refresh after managing an automation on GitHub to update the Automations view.

H2: Cloud automation security and usage
Cloud automations perform unattended work with the tools you allow. Grant only the tools the task needs, use narrowly scoped prompts and event filters, and review a manual run before enabling recurring work. Don't assume that local approval or sandbox settings apply to GitHub's execution environment.
An Only me automation is private, but its run sessions and logs can be visible to people with repository access. Don't put secrets in prompts. Use the repository's supported secret configuration and review GitHub automation security and safety.
Scheduled runs, event-triggered runs, and follow-ups can consume service usage. Check GitHub automation billing and your organization's policies before enabling frequent triggers.

H2: Cloud automation limitations
Cloud automation support in VS Code currently has these limitations:
Available repositories, event types, filters, models, and tools depend on GitHub service support and your account's permissions.
A cloud automation uses the cloud model and tool configuration. It doesn't accept local mode or approval settings, custom agents, or local MCP configuration.
Cloud automations don't support end dates. Disable or delete the automation when scheduled or event-triggered work should stop.
Unsupported trigger configuration must be managed on GitHub. It isn't replaced when you edit other supported fields.
