The Agents window provides an agent-first interface in Visual Studio Code for delegating and coordinating tasks across projects. Run independent tasks in parallel, monitor their progress, and review results in one place. Use chat in the editor when you want to collaborate with an agent alongside the code you're editing or debugging.
This guide follows the workflow from choosing where an agent makes changes to monitoring, validating, and integrating its work. Start with one task, then add independent tasks as needed. If you're new to agent-assisted coding, first complete the agents quickstart.
H2: Open the Agents window
Select Open in Agents in the VS Code title bar, or run Chat: Open Agents window from the Command Palette (⇧⌘P (Windows, Linux Ctrl+Shift+P)). The window opens alongside your main editor window.
If you're already signed in to GitHub in VS Code, you'll also be signed in when the Agents window opens. From the command line, use code --agents.
H2: Agents window interface overview
The Agents window separates managing work across projects from working on an individual task. Use the Primary Side Bar to organize sessions and access automations and customizations, the central session area to collaborate with agents, and the Secondary Side Bar to inspect and validate the active session's work.
The available tools depend on the session and enabled features.
H3: Understand the active session
Selecting a session makes it the active session and determines which project and conversation the session tools apply to. When several session panes are visible, select a pane to make it active. The active session is highlighted in the sessions list.
Before you send feedback or run a command, confirm which session is active. Terminal commands and tasks run in that session's folder or worktree, and browser tabs belong to the session where you open them.
Quick chats have no project workspace, so they don't show workspace-specific files and changes.

H3: Choose where an agent makes changes
For a Git workspace you can choose between applying changes in the current branch or a new worktree. Use the isolation dropdown above the input to choose where the agent edits files.
Choosing a base branch for New Worktree doesn't switch the branch in your active workspace.
Git-ignored files, including dependencies and local configuration, are also absent from new worktrees by default. Run your project's setup or configure which ignored files to include.
Dev Container sessions work directly in the container workspace and don't support New Worktree. See Run a session in a Dev Container.
Worktrees isolate working files, not the agent's access to your machine or external services. Either isolation mode supports the permission levels offered by your harness. For operating system-level restrictions, configure agent sandboxing or use cloud sessions.
H2: Work with multiple sessions
You can run multiple agent sessions in parallel, either in the same project or across different projects. Each session has its own conversation and task context, so you can delegate independent work and review one result while another session continues. For example, one session can implement a feature in one project while another investigates a bug in a different project.
Use separate sessions for independent tasks you want to track and review separately. For related conversations you want to keep together, work with multiple chats in a session.
To add another task, select New Session, choose its project, and submit a prompt. You don't need to wait for the other sessions to finish. Switch between them in the sessions list to check progress, answer questions, or give feedback. Sessions can run in parallel without being displayed side by side. Arrange sessions in a grid when you want to keep several conversations visible.
For parallel changes in the same repository, use separate worktrees to keep edits apart. Separate sessions or chats don't automatically isolate files: those using the same folder can edit the same files. Choose tasks that can proceed independently. If one depends on another's result, complete that prerequisite first. For a walkthrough, follow Delegate two tasks without mixing their changes.
Use the sessions list to check status and change statistics. Select a session to inspect its conversation:
If it needs input, answer its question or review the approval request.
While it works, check that its changes stay within the task's scope. Send corrections to that session, not another task's conversation.
When it finishes, review and validate the result. A completed response isn't proof that the task is correct.
Confirm the active session before sending feedback or running commands. For steering and stopping requests, see Use chat. To group, pin, or find sessions, see Organize sessions.
H3: Arrange sessions in a grid
To keep two sessions visible, right-click a session in the list and select Open to the Side. To start another session without replacing the current pane, hold Alt (Option on macOS) and select New Session.
Drag a session to the top, bottom, left, or right edge of another session to create a horizontal or vertical split. A placement preview shows where the session appears.
Only one pane is active at a time. Selecting another session in the list replaces an unpinned active view.
When multiple panes are visible, use the session header's Session Layout menu to arrange or resize them. Maximize expands one pane, and Restore Size returns to the grid. These actions are separate from Session Layout.
H2: Review and finish an agent session
When an agent finishes a task, use the Agents window to review its changes, request revisions, and validate the result. Once the work meets your requirements, commit the changes and integrate them into your project, either locally or through a pull request.
Select the session you want to review to make its files, changes, and tools active.
For more in-depth coding or debugging, select Open in Editor to continue a supported project session in the main editor window, with the editor, debugger, and other development tools alongside the conversation.
H3: Inspect workspace files and changes
In the Secondary Side Bar, use Files to browse the workspace or worktree and Changes to review edits. In Changes, choose Branch for the branch diff, Uncommitted for pending changes, Session for the session's edits, or Last Turn for its latest turn. Review the full relevant change, not only the latest response.
Check that the result meets your requested outcome, preserves required behavior, and contains no unrelated edits.
To provide immediate feedback, open a file's diff, select a range, and use the feedback controls to leave range-based feedback for the agent. For detailed review and recovery controls, see Review AI-generated code edits.

H3: Commit changes
For uncommitted changes, open Changes, select Uncommitted from the changeset dropdown, and then select Commit. VS Code generates a commit message and commits all current changes in the session's Git repository, so review them first. The available Git actions depend on the session type.
Generating the commit message requires signing in to GitHub Copilot, even when the session uses another provider's credentials.
The Commit action uses git commit --no-verify, which skips pre-commit and commit-msg hooks. Commits made by Create PR also skip these hooks. Run your project's required checks before using either action.
H3: Integrate the result
Committing records the changes but doesn't necessarily put them in the branch where you need them:
With Branch isolation, edits are already in the selected folder. Follow your normal branch and pull request workflow.
With New Worktree, edits remain in the separate worktree. Integrate the reviewed branch into your target branch locally, or create a pull request. For a parallel-work example, follow Integrate and retest.
After combining changes from multiple sessions, rerun the relevant checks on the combined result. Keep the sessions available until that validation is complete, then mark finished sessions as done.

H3: Remove a pull request from a session
To remove a pull request artifact without closing the pull request on GitHub, right-click its pill above the chat input and select Remove Pull Request Artifact from Session. If the pill contains multiple pull requests, open its dropdown and select the action for the relevant pull request.
A separate association, such as the one created when you start a session from a pull request, remains unchanged.
